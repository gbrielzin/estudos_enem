# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal ENEM study system (Portuguese-language codebase/comments) for one user (Gabriel) preparing to retake the exam. `core/` is a from-scratch rewrite of a legacy prototype that lives one directory up (`enem_gi/main.py`, `enem_gi/app.py`) — the legacy system stored everything in a single CSV and had real bugs (schema collisions between scripts writing the same file, string-fragmented taxonomy like "Matemática Básica" vs "matemática básica", one video = one question with no room for a second resolution). `core/` replaces the CSV with a SQLite database (`enem.db`) plus a relational schema specifically to make those bug classes impossible by construction. The project root has a local git repository (initialized 2026-08, nothing pushed anywhere) — commit before risky changes, same as any other repo.

Do not "fix" the legacy files in the parent directory as part of work here — `core/` intentionally does not import from them except for one deliberate exception (see Cross-directory dependency below).

## Commands

There is no test suite, linter, or build step. This is a Streamlit app + a set of one-off/maintenance scripts.

- Run the app: `streamlit run cartao_resposta.py` (from inside `core/`)
- Load/update `enem.db` from source-of-truth CSVs: `python reconstruir_base.py` — backs up `enem.db` first (via `backup_db.py`) then updates in place; idempotent, safe to rerun (see the note under Architecture below)
- Smoke-test `db.py` in isolation: `python db.py` — this writes to `enem_teste.db`, never to `enem.db` (see the `__main__` block); safe to run anytime
- Extract an official gabarito from an INEP PDF: `python extrair_gabarito_pdf.py <arquivo.pdf> <ano> [caderno] [--ciencias]` — requires the `pdftotext` CLI (poppler-utils) on PATH; writes `gabaritos_reais/gabarito_<ano>_<caderno>_OFICIAL.csv` (Matemática, itens 136-180) or `..._CIENCIAS_OFICIAL.csv` (`--ciencias`, itens 91-135) — same PDF covers both areas, run it twice (with/without `--ciencias`) when both are missing for a caderno. `caderno` defaults to `azul` — always pass it explicitly for any other booklet color, e.g. `amarelo`/`cinza`/`rosa`, or this silently targets the azul filename; refuses to overwrite an existing file unless `--sobrescrever` is passed
- Extract question TEXT (enunciado + alternatives) from an INEP exam PDF (the PV/prova file, not the GB/gabarito one): `python extrair_enunciados_pdf.py <arquivo.pdf> <ano> <caderno> [--aplicar] [--sobrescrever]` — needs `pymupdf` (`import pymupdf`, not the deprecated `import fitz`); without `--aplicar` it only writes a review file (`scratch_enunciados_<ano>_<caderno>.txt`, gitignored) for manual spot-checking — nothing touches the DB until you've read it and pass `--aplicar`. With it, writes `questoes.enunciado_texto` via `db.atualizar_enunciado()` (never touches gabarito/materia/tentativas — fully separate from the gabarito pipeline above). ~40% of real questions cite "figura/gráfico/tabela/esquema" and get a ⚠️ prepended to their text — INEP draws those as vector paths inside the PDF, not embedded image objects (confirmed: `page.get_image_info()` returns empty on pages with a visible diagram), so this script alone can't recover them (see `extrair_figuras_pdf.py` below for the vector-path case); a real minority additionally have NO textual trace at all that something is missing (e.g. a comic strip referenced only as "a tirinha"), which the keyword heuristic can't catch — treat any prova run through this script as needing a human pass against the real PDF for the flagged (and ideally unflagged-but-short) questions before trusting it fully. `numero` in the PDF must match the caderno's own numbering (pass the actual color, same footgun as the gabarito script).
- Recover the figure/graph/table itself from the same PDF (vector paths, not embedded images — see above): `python extrair_figuras_pdf.py <arquivo.pdf> <ano> <caderno> [--aplicar] [--sobrescrever]` — uses `page.cluster_drawings()` (native to `pymupdf`, groups nearby vector paths into a bounding rect) to crop each figure as a PNG into `core/enunciados/<id_questao>.png`, the same folder/naming the manual enunciado-image uploader in `cartao_resposta.py` uses. Associates a crop with the right question by finding each "Questão N" marker's on-page position via `page.search_for()` and assigning every cluster to the last marker that precedes it in ENEM's 2-column reading order (`(coluna, y0)`, left column before right, EXCEPT `_duas_colunas_de_verdade()` falls back to plain `y0` on a page whose own "Questão N" markers all sit in one column — real case: a question with diagram-based alternatives can print at full page width, and treating its right-half images as "after" the left column silently attributed two of them to the NEXT question instead) — a cluster before any marker on its page inherits the previous page's last question, EXCEPT on a page with under ~200 chars of text (`_MIN_TEXTO_PAGINA`), treated as a cover/divider page that owns no question and passes nothing forward, which is what keeps a colophon-page logo from being misattributed to the last real question. Multiple clusters for one question on the same page merge into one crop (union rect); clusters split across two different pages for the same question keep only the page with more total area — `enunciado_imagem_path` holds one path, not a list. Without `--aplicar`, still writes the PNGs (so you can eyeball them) but skips the DB write. Validated by hand against a real PDF (2020 azul): spot-checking crops against the source PDF (including the last question, right next to the colophon page, and the full-page-width exception above) is what caught the column bug in the first place — worth a repeat spot-check on any new prova, not a one-time validation to trust blindly.
- Import enunciado/alternativas/imagem from the public enem.dev API instead of a local PDF (covers 2009-2023 only — a 404 means the year isn't in the API yet, e.g. 2024 at the time this was written): `python importar_enem_dev.py <ano> [--aplicar] [--sobrescrever]`. Exists because the API has content the vector-path pipeline above structurally cannot reach — a real embedded photo (e.g. the 2020 "tirinha do Garfield" question, a comic strip, not a vector drawing) or per-alternative images already split one-file-per-letter (e.g. the 2020 circuit-diagram question, one clean PNG per A-E instead of `extrair_figuras_pdf.py`'s stacked union crop) — verified against both by hand before trusting it, alternatives text matched what was already loaded and `correctAlternative` matched the official gabarito. The API doesn't document which caderno color its `index` numbering follows, so `_confirmar_caderno_azul()` cross-checks `correctAlternative` against the azul gabarito already in the DB before writing anything for that year, aborting instead of importing under the wrong id_questao if under 90% agree. Like the other two scripts, only fills `enunciado_texto`/`enunciado_imagem_path` on a question that already exists (never inserts, never touches `materia`/`gabarito` — the API's `discipline` is too coarse for this project's materia taxonomy anyway) — and specifically also fills just the missing image on a question that already has text from the PDF pipeline (the Garfield case), stripping `extrair_enunciados_pdf.py`'s "pode faltar figura" ⚠️ prefix once the real image is confirmed downloaded, but only after the download actually succeeds. The API's own pagination has an inclusive-boundary bug (the last item of one page reappears as the first item of the next), deduped by `index` before use. Requires `requests` and `Pillow` (both already transitive deps of this project, now declared explicitly).
- One-off backfill scripts (`classificar_2024.py`, and historically similar ones) are meant to be run once and read top-to-bottom before rerunning — they hardcode question numbers/answers for a specific gap in the data

Dependencies: `streamlit`, `pandas`, `pymupdf` (see `../requirements.txt`), and, transitively through `coletar_videos.py` → `main.py`, the Google API client libraries used for YouTube auth.

`reconstruir_base.py` no longer deletes `enem.db` — it backs it up (via `backup_db.py`) and updates in place, idempotently. `db.carregar_gabarito_csv(..., preservar_materia_classificada=True)` is what makes that safe: an already-`classificado` question keeps its current `materia` even under `sobrescrever=True`, so bulk-loading a gabarito CSV (whose `materia` column is often just a placeholder like `sem_video_pendente`) can't regress a classification gained later via video-title scraping or manual triage. UI callers (Admin paste, Triagem) don't pass that flag — there, `sobrescrever=True` is deliberate human correction and should win.

## Architecture

### Layering rule (important, stated explicitly in db.py's docstring)

`db.py` is a leaf module: it imports nothing from `main.py`/`app.py`/any UI module, and has no dependencies outside the standard library. Every other module in `core/` imports *from* `db.py`, never the reverse. If a UI module ever needs something that currently lives in the parent `main.py`, that logic must be promoted into `core/` (or a new shared module) — never imported back from `main.py` into `db.py`. The one sanctioned exception to "never depends on the parent directory" is `coletar_videos.py`, which does `sys.path.insert(...)` to import `main.py` from the parent for its already-working YouTube OAuth/playlist-fetch code (`autenticar_youtube`, `extrair_playlist_id`, `buscar_todos_os_videos`) rather than duplicating it.

### Data model (`schema.sql`, mirrored by `TAXONOMIA_VALIDA` in `db.py`)

- `questoes` — one row per real exam question. Primary key is `id_questao`, a canonical string `"{ano}_{caderno}_{numero}"` (e.g. `2024_azul_136`), generated by `gerar_id_canonico()`. Using this instead of e.g. a video link as identity means a question's identity doesn't depend on whether it has a resolution video yet.
- `resolucoes` — many-per-question (video and/or text resolutions), the main limitation the old CSV model couldn't express. Full CRUD: `inserir_resolucao()` (dedupes), `resolucoes_da_questao()` (now includes `id_resolucao`), `editar_resolucao()`, `apagar_resolucao()` — the delete is wired as a 🗑️ next to each video in the wrong-answer review on Cartão-resposta, for a link the cross-caderno auto-linker (`coletar_videos.py`) got wrong.
- `tentativas_usuario` — append-only log of every answer attempt, with three sanctioned exceptions, all going through `_recomputar_estado_revisao(id_questao, conn)` (replays that question's full remaining history through `_calcular_leitner()` from streak 0, since streak/interval are cumulative — editing or deleting a row anywhere in the sequence can change what every later row would have computed; a full replay is the only way to get the correct final state, not an incremental patch):
  - the gabarito-correction path described below (`inserir_questao(sobrescrever=True)` changing `alternativa_correta`, recalculating `resultado` for existing attempts)
  - `db.desfazer_tentativas(ids_tentativa)` — "I mismarked what I just submitted": only deletes a question's attempt when that was its ONLY one ever; a question with prior history is left untouched and reported as skipped. Wired to a "Desfazer essa correção" popover right after grading, scoped to the just-submitted batch only.
  - `db.apagar_rodada_tentativa(ano, caderno, grande_area, numero_tentativa)` / `db.editar_resposta_tentativa(id_tentativa, nova_resposta)` — deliberate edit/delete of ANY past round (has prior history or not), for a genuinely wrong or duplicated submission noticed later. `numero_tentativa` here is the same value `resumo_por_tentativa()` derives on the fly, not a stored id — deleting a round removes every question's attempt at that position and cleans up its `nomes_tentativas` row too; editing rewrites `resposta_escolhida`/`resultado` in place and clears `tipo_erro` (a classification tied to the old letter no longer applies). Wired to "✏️ Editar respostas" / "🗑️ Excluir esta rodada" popovers per round on the "Simulados já feitos" page (`db.detalhe_rodada()` feeds the per-question editable grid) — deletion requires an explicit confirm checkbox first, matching Admin's "Apagar prova" pattern.
- `estado_revisao` — one row per question ever attempted; the mutable "what to review today" pointer, deliberately kept separate from the immutable `tentativas_usuario` log.
- `historico_alteracoes` — audit trail: whenever `inserir_questao(sobrescrever=True)` changes an already-stored `materia` or `alternativa_correta`, the change (and how many past attempts got their `resultado` recalculated) is logged here.
- `topicos_validos` — DB-side mirror of `TAXONOMIA_VALIDA`; not enforced via FOREIGN KEY on purpose (see below).
- `nomes_tentativas` — optional free-text label per `(ano, caderno, grande_area, numero_tentativa)`, purely cosmetic (e.g. "fiz cansado à noite"). `numero_tentativa` is never generated or owned by this table — it's the same value `resumo_por_tentativa()` derives on the fly via `ROW_NUMBER()` over `tentativas_usuario`; this table only attaches a name to that number, via `db.nomear_tentativa()`/`db.nomes_tentativas()`.
- `redacoes` — essay/writing-practice log, deliberately standalone (no `FOREIGN KEY` to anything else — a redação isn't about a `questao`). Guards, doesn't grade: `nota`/`erros_ortograficos`/`observacoes` are typed in by a human after the fact, once the essay has been corrected somewhere else (`fonte_correcao` CHECK'd to `'propria'`/`'externa'`/`'oficial'`, nullable — "not graded yet" is a real, expected state, not a missing row), because the system has no way to actually evaluate a redação itself. `arquivo_path` optionally holds a photo/PDF of a handwritten essay, uploaded via the page's own `st.file_uploader` (same re-save-on-every-rerun footgun as any other uploader in `cartao_resposta.py` — gated behind the same upload-generation-counter pattern, see the file-uploader warning below). CRUD via `db.salvar_redacao()` / `db.listar_redacoes()` / `db.atualizar_redacao()` / `db.apagar_redacao()` / `db.temas_redacoes_usados()` (the last one backs a "reuse an existing tema" dropdown, since the same essay prompt sometimes gets rewritten more than once).

### Closed taxonomy + classification pipeline

Subject (`materia`) values come from a closed set, `TAXONOMIA_VALIDA` in `db.py` (mirrored, for reference, in `schema.sql`'s `topicos_validos` table and in `prompt_extracao_gabarito.md`'s taxonomy block — keep these in sync manually if you add a subject). Text goes through this pipeline before being checked against the taxonomy:

1. `normalizar_texto()` — lowercase, strip accents (NFKD), collapse whitespace to `_`.
2. `canonicalizar_materia()` — first checks `SINONIMOS_MATERIA` (exact synonym map, e.g. `funcao_afim` → `funcao_1_grau`), then `_PADROES_MATERIA` (regex families for things like "função de/do 1º/1/primeiro grau" that a synonym dict can't enumerate practically).
3. Checked against `TAXONOMIA_VALIDA`.

There is intentionally **no FOREIGN KEY** from `questoes` to `topicos_validos`: a question whose subject doesn't match anything in the closed taxonomy still gets written to `questoes`, just with `status_classificacao='nao_classificado'`, instead of being rejected or dropped. This is what feeds the triage workflow — see below. When adding a new synonym/pattern, run "Reclassificar com as regras atuais" (triagem.py → `db.reclassificar_pendentes()`) to reprocess already-pending rows; adding the mapping in code alone does not retroactively reclassify existing data.

### Manual triage survives full rebuilds

`triagem.py` lets a human assign a subject to `nao_classificado` questions. Because `reconstruir_base.py` deletes and rebuilds `enem.db` purely from the official gabarito CSVs (which know nothing about manual corrections), every manual classification is *also* persisted to `gabaritos_reais/correcoes_manuais.csv`, and `reconstruir_base.py` explicitly replays that file after loading the official gabaritos. If you add another mutation path that changes a question's `materia` outside of `inserir_questao(sobrescrever=True)`, it needs the same "persist somewhere `reconstruir_base.py` will replay" treatment or it will silently be lost on the next rebuild.

### `sobrescrever` semantics and answer-key corrections

`inserir_questao(..., sobrescrever=True)` updates a row in place, keeping the same `id_questao` (so existing `resolucoes`/`tentativas_usuario` foreign keys stay valid). If the correct answer (`alternativa_correta`) actually changes, every existing attempt for that question has its `resultado` (`acertou`/`errou`) recalculated against the new answer, and the change is logged to `historico_alteracoes`. This is deliberate: a later, more trustworthy source (e.g. an official PDF gabarito) can correct an earlier guess without silently leaving stale acertou/errou values behind.

### Spaced repetition (simplified Leitner)

`_calcular_leitner()` in `db.py`: wrong answer → streak resets to 0, next review in 1 day. Correct answer → streak += 1, interval = `2^(streak-1)` days, capped at `TETO_INTERVALO_DIAS` (90). The interval is always recomputed from the current streak rather than incrementally adjusted, so it can never drift from a corrupted intermediate state — it's fully reconstructible from `tentativas_usuario` history. `registrar_tentativa()` is the *only* function that should write to both `tentativas_usuario` and `estado_revisao` (keeps them from diverging via separate writes).

`resposta_escolhida` is nullable (`CHECK(... IN ('A'..'E') OR resposta_escolhida IS NULL)`, migrated in-place by `inicializar_banco()` for any database still on the old NOT-NULL constraint — SQLite can't ALTER a CHECK, so this rebuilds the table and copies every row across, guarded by a `sqlite_master.sql` text check so it only runs once). `NULL` means the question was left blank — it's a real, deliberate tentativa (always `resultado='errou'`, since not answering can never be correct), not the absence of one. Before this, `_renderizar_grade_questoes()` skipped blank questions entirely: they never reached `registrar_tentativa()`, so they were invisible to every stat built on `tentativas_usuario` (taxa de acerto, prioridade de estudo, Leitner scheduling) and inflated the displayed percentage (44/44 shown instead of 44/45 when one of 45 was left blank). `editar_resposta_tentativa(id_tentativa, None)` can set an existing tentativa back to blank symmetrically. The "⚡ Preenchimento rápido" quick-fill in `cartao_resposta.py` must explicitly set a skipped position's radio back to `"—"` (not just skip touching it) — leaving a prior letter untouched there was the original bug report: pasting a corrected sequence with `*` over an already-filled position silently kept the old letter.

### Study-decision layer (explicable prioritization, recent confidence, weekly trend, study planner)

Four additions on top of `prioridade_de_estudo()`, added together (2026-09) to turn the existing pipeline — `questoes` → `tentativas_usuario` → `estado_revisao` → Leitner → prioridade → stats — into something that also says *what to do with today's block of time*, not just *what the numbers are*. None of these persist anything new; all four are pure functions recomputed live from `tentativas_usuario`/`questoes`, same as every other analytics function in `db.py`.

- **`prioridade_de_estudo()` explicabilidade**: each ranking entry now also carries an `"explicacao"` dict (`peso_recorrencia`, `contribuicao_recorrencia`, `contribuicao_taxa_erro` — the two weighted terms that sum back to `score_prioridade`). Purely additive key, doesn't break any existing caller (including `reconstruir_base.py`'s own end-of-run printout). Exists so the UI can answer "why is this the priority" with the actual arithmetic instead of just the final number — see the "🔍 Por que..." expander in `render_analise()`.
- **`confianca_recente_por_materia(grande_area, janela=5)`**: complements the *all-time* `taxa_acerto_por_materia()` with a *recency* signal — the last `janela` tentativas per matéria, classified `alta`/`media`/`baixa` (`LIMIAR_CONFIANCA_ALTA`/`LIMIAR_CONFIANCA_BAIXA`, ≥80%/≤20% of the recent window). Exists because a 50% lifetime average hides two very different situations ("always wrong, last 5 mostly right" vs. "always right, last 5 mostly wrong") that a single cumulative percentage can't distinguish. `amostra_pequena` flags when the matéria's whole history is shorter than `janela` (same semantics as `MIN_AMOSTRA_CONFIAVEL` elsewhere, just against a different denominator).
- **`evolucao_semanal_por_materia(grande_area, n_semanas=4)`**: buckets tentativas by SQLite calendar week (`strftime('%Y-%W', ...)`), takes the last `n_semanas` *with real activity* (an empty week doesn't count as one of the N), and compares the older half of that window against the newer half per matéria — never a single first-point-vs-last-point comparison, which a single sparse week would make meaningless. Returns `maior_evolucao`/`maior_risco`/`estagnado`, but **only from candidates with `>= MIN_AMOSTRA_CONFIAVEL` tentativas in BOTH halves** (`candidatos_confiaveis` filter) — the first version of this function picked its headline straight from `candidatos_delta` and it immediately surfaced a materia with 1 wrong attempt in week 1 and 1 right attempt in week 2 as "+100% evolução", which is exactly the kind of manufactured confidence `prioridade_de_estudo()`'s own `sem_dados` split already exists to avoid elsewhere — caught by the function's own test (`TestEvolucaoSemanalPorMateria`) before shipping, not by inspection. `estagnado` additionally requires `fim_pct < LIMIAR_ESTAGNACAO_PCT` (60%) — flat at 95% isn't a problem worth flagging, flat at 40% is. With the DB's current real history (only 2 distinct weeks of activity so far), this mostly returns `None`s for now — it gets more useful purely as more weeks of real data accumulate, nothing to fix.
- **`gerar_plano_de_estudo(minutos_totais=120)`**: turns a number of available minutes into ordered time blocks — revisões vencidas (capped at `FRACAO_REVISAO_VENCIDA`=25% of the total, even if the overdue queue is much bigger — the point is a sustainable daily dent, not clearing 468 overdue questions in one sitting), prática geral per area (split between matemática/ciências proportional to each area's overall error rate — worse area gets more minutes), foco isolado on the single highest-`score_prioridade` matéria across both areas (capped at `FRACAO_FOCO_FRAQUEZA`=20%), and redação (fixed `MINUTOS_REDACAO_SUGERIDO`=20min, only if `DIAS_SEM_REDACAO_PARA_SUGERIR`=7+ days have passed since the last one, or none exists yet). Every block carries a `"motivo"` string — no block is ever minutes-only, matching the same explicability principle as the ranking above. The foco block specifically also looks up `_tipo_erro_predominante()` (private, only this function calls it) against `analise_por_tipo_erro()` — a field (`tipo_erro`: erro de conta/pegadinha/conteúdo) that existed in the schema and UI already but wasn't consumed by any analytical function before this — and folds a one-line "maioria dos erros aqui são de X" into the motivo, with an extra nudge toward Modo Aula Base specifically when the dominant type is `erro_de_conteudo` (a real content gap, not carelessness — the same distinction `manual_prioridade_de_estudo.md` already argues for by hand). `minutos_alocados` in the return can be less than `minutos_totais` when there isn't enough data to fill the request (e.g. a near-empty database) — reported explicitly rather than stretching a block to force the numbers to match; a genuinely empty database still returns exactly one block ("Redação" — "nenhuma redação registrada ainda" is on its own a valid reason for that block to fire, verified by its own test). Surfaced as "📋 Plano de hoje" at the top of the Calendário page, with a `st.slider` for `minutos_totais` (session_state-backed, not persisted to `configuracoes` — this is a per-view choice, not a setting).

Deliberately **not** built alongside these: a hierarchical tema→subtema→habilidade taxonomy (would mean reclassifying all 754 already-classified questions against a new schema, which needs the same kind of human judgment call that `triagem.py` already exists for — not something to migrate unilaterally), and any ML/LLM-based version of confiança/evolução (587 tentativas, single user, is still the same "not enough data to justify it yet" situation `SYSTEM_DEEP_DIVE.md`'s section 10 already covers — these four additions are still the deterministic-heuristics side of that line, just a level up from Leitner/prioridade alone).

### `gabaritos_reais/` naming convention

Source-of-truth CSVs consumed by `reconstruir_base.py`, matched by filename regex:
- `gabarito_<ANO>_<CADERNO>_OFICIAL.csv` → Matemática
- `gabarito_<ANO>_<CADERNO>_CIENCIAS_OFICIAL.csv` → Ciências da Natureza (same exam day/caderno, different `grande_area`)

Required CSV columns: `numero,materia,gabarito` (optional per-row `grande_area` override). Math and Ciências for the same year/caderno are stored as **separate** "provas" throughout the system (never merged into one 45+44-question grid), since they're graded and studied independently.

### Multiple cadernos (booklet colors) of the same year

A real INEP exam prints the same items in 4+ colors (azul/amarelo/rosa/cinza, and 2024 added verde) with different item ORDER per color — same content, different `numero`. Each `(ano, caderno, grande_area)` combo is stored as its own fully independent set of `questoes` rows (own `id_questao`, own `materia` classification, own attempts) — confirmed, deliberate design (Gabriel wants each color he practices to count as its own separate simulado attempt for média móvel/priority stats, not merged into one). Loading a new color for a year already partially loaded is just running `extrair_gabarito_pdf.py`/`reconstruir_base.py` again with that `caderno` — no special-casing needed, this is exactly the same code path as loading a brand-new year.

`db.simulados_completos_disponiveis()` (backs "Simulado completo" and the Calendário checklist) enumerates every `(ano, caderno)` pair that has BOTH areas loaded — a year can produce more than one entry (2024 has both azul-complete and amarelo-complete). An earlier version stored only one caderno per `(ano, area)` in a plain dict, so a second color for the same area silently overwrote the first the moment it was loaded — fixed by keying on sets of cadernos per area and emitting one combo per same-caderno match, falling back to a cross-caderno combo (2023's azul-math/cinza-ciências case) only when each area has exactly one candidate caderno. Any UI that lists these combos must label by caderno too (`f"{ano} — {caderno}"`), not just by `ano` — a bare-year key collides the same way the old data layer did.

### Cross-caderno video linking (`coletar_videos.py`)

The channel (Xequemat) pastes, in the video's YouTube **description** (not title), the same item's number in every color — confirmed against the real API response, and the opposite order from what the title's own "Questão N - Caderno X" format would suggest (color first, then number):
```
Caderno Azul - 136
Caderno Amarelo - 164
Caderno Rosa - 150
Caderno Cinza - 166
```
`extrair_cadernos_da_descricao()` parses this block; `processar_playlist()` uses it to link the SAME video (and propagate the SAME materia, if extracted from the title and the target question is still `nao_classificado`) to every color's corresponding `id_questao` — not just the color passed as the `caderno` argument. A color with no gabarito loaded yet just lands in the `cruzados_sem_questao` result bucket (harmless) — re-running the playlist collection later, after loading that color, picks up the missing links retroactively (no need to special-case "already tried this before"; `db.inserir_resolucao()`'s existing dedup makes it idempotent). Older videos without this description block fall back to the original single-caderno-only behavior unchanged.

### App structure (`cartao_resposta.py`)

Single Streamlit entry point with a sidebar-driven page switch (not a multi-file Streamlit app): Cartão-resposta (answer sheet + grading), Minha análise (dashboards: study-priority ranking blending recurrence x error rate — now with a per-matéria recent-confidence column via `confianca_recente_por_materia()` and a "🔍 Por que..." expander unpacking the top pick's score via `prioridade_de_estudo()`'s `explicacao` field, plus a weekly-trend section via `evolucao_semanal_por_materia()` — error-type breakdown, streak/rank gamification), Simulados já feitos (every prova with at least one tentativa, grouped by round via `db.simulados_feitos()`/`db.resumo_por_tentativa()`, with per-round rename/edit-answer/delete-round and a copy-pasteable `st.code()` text summary meant for feeding a wrong-question review into an external AI chat), Prova com enunciado (beta) (`render_prova_beta()` — same `_renderizar_grade_questoes()` core as Cartão-resposta, restricted to provas with `enunciado_texto` populated via `extrair_enunciados_pdf.py`, kept as its own page rather than folded into the main flow because ~40% of extracted enunciados are flagged ⚠️ as possibly missing a figure — deliberate user request to keep this experimental surface separate from the trusted main workflow; also renders with `estilo_exame=True`, a one-question-per-row layout with the full enunciado always visible above its answer radio and no quick-fill, deliberately mimicking a real printed exam page instead of the compact 3-column answer grid, per explicit user request; the radio itself tries to show each alternative's own text next to its letter via `_separar_alternativas()` — trusts ONLY the last 5 non-empty lines of `enunciado_texto`, and only if they come in strict A,B,C,D,E order, as the signal that they're the real alternatives (a bare per-line regex would false-positive on any stem sentence starting with the article "A", and would corrupt on a diagram-based-alternatives question where the extracted order isn't A→E at all — see `extrair_figuras_pdf.py`'s question-93 case below); when it can't confidently separate them, falls back to a plain horizontal letter-only radio instead of risking a wrong split. `format_func` on that radio takes `alternativas` as a default arg, not a closure over the loop variable — the loop redefines `alternativas` on every question, and a plain closure would give any later re-invocation of an earlier question's `format_func` the LAST question's dict instead of its own (harmless for real Streamlit, which only calls `format_func` synchronously inside that same `st.radio()` call, but breaks `AppTest`, which retains the function object to recompute the selected index later), Calendário (`db.plano_periodizacao()` phase + weakness ranking + `db.progresso_simulados()` checklist, all derived live from real data, never a fixed schedule; leads with "📋 Plano de hoje", `gerar_plano_de_estudo()` turning a `st.slider`-picked minute budget into time-boxed, self-explained blocks — see Study-decision layer above), Objetivos (countdown, freeform "why", target scores vs. actual practice accuracy, photo vision board in `core/vision_board/`), Redação (`render_redacao()` — logs an essay attempt: tema (reusable from a dropdown once at least one exists, via `db.temas_redacoes_usados()`), date, optional pasted text and/or an uploaded photo/PDF of a handwritten essay, and a nota/spelling-error-count/observações filled in later once it's actually been corrected elsewhere — same "store, don't grade" split as the `redacoes` table itself, see Data model above), Coletar vídeos (delegates to `coletar_videos.py`), Triagem (delegates to `triagem.py`), Admin (backup, daily goal, exam date, paste-CSV gabarito loader, whole-prova delete, single-question edit/delete via `db.detalhe_questao()`/`db.apagar_questao()` — for a bad row inside an otherwise-good CSV paste, without nuking the other 44 questions, `historico_alteracoes` viewer), Guia do Estudante (renders `guia_estudante.md` / `prompt_extracao_gabarito.md` verbatim). Theme (`.streamlit/config.toml` + `ui_theme.py`, injected once per run via `ui_theme.injetar_tema()`) applies globally regardless of which page function renders — light background (white/`#FAFAFA`) with near-black text and a darker accessible green (`#15803D`, not the original neon `#39FF14`) for text-bearing accents, since neon-on-white fails WCAG text contrast; the original neon green survives only where color doesn't need to be read (hover glow, streak-calendar fill). The nav drawer (hamburger + gaveta in `ui_theme.navegacao_lateral()`) deliberately keeps the old dark/neon look regardless of page theme — it's navigation chrome, not reading content, and every one of its CSS rules sets its own color explicitly rather than inheriting from `[data-testid="stMain"]`. Changed from an all-dark "neon terminal" theme in 2026-08 (user request, validated first as a beta-only light treatment on Prova com enunciado before being promoted app-wide). `configuracoes` (key-value table in `schema.sql`) holds everything user-editable that isn't question/attempt data: `data_prova`, `data_inicio_plano` (set once, anchors `plano_periodizacao()`'s phase math -- never overwritten except when the exam date itself is edited in Admin), `meta_diaria`, `meta_nota_matematica`/`meta_nota_natureza`, `motivo_pessoal`.

Any `st.file_uploader` that saves on presence of a value (not gated behind its own `st.button`) is a bug waiting to happen: the uploader keeps its value across reruns until its `key` changes, so an unconditional `if arquivo: salvar(); st.rerun()` re-saves the same file every rerun forever (found and fixed once already in the vision-board uploader -- one test upload became ~500 copies in seconds). Every file-save path in this file either gates on an explicit button click, a widget `key` that increments after success, or both.

Cartão-resposta itself has 4 "Modo" options, all converging on `_renderizar_grade_questoes(questoes, sufixo)` -- the shared grid/grading/error-review core (extracted out of `_renderizar_bloco_prova()` in 2026-08 specifically so it could be reused by more than one exam-shaped source). "Uma prova por vez" and "Simulado completo" fetch via `db.listar_questoes_da_prova()` (one exam; `_renderizar_bloco_prova()` also shows the prova-specific attempt history). "Revisão de hoje" fetches via `db.questoes_para_revisar()` + `db.questoes_por_ids()` (whatever's overdue, any exam, order preserved). "Praticar por matéria" fetches via `db.questoes_por_materia()` (one subject, every year mixed together on purpose -- the one place in the app that deliberately breaks the "never mix exams" rule, because the point is cross-year practice of a weak subject). `_renderizar_bloco_prova()` is still called twice on one page (once per tab) for "Simulado completo" running Matemática and Ciências back to back -- every widget/session_state key is suffixed with `ano_caderno_area` (or the mode's own sufixo) to avoid collisions between calls.

Enunciado (`questoes.enunciado_texto` / `enunciado_imagem_path`, updated via `db.atualizar_enunciado()`) renders inline in the grid when present, with its own editor rendered OUTSIDE `_renderizar_grade_questoes()`'s `st.form(...)` -- a form allows exactly one submit button, so per-question "save enunciado" buttons can't live inside it. Uploaded images land in `core/enunciados/<id_questao>.<ext>`.

### `guia_estudante.md` / `prompt_extracao_gabarito.md` / `manual_prioridade_de_estudo.md`

The first two are not documentation about the code — they're copy-pasteable prompts for use in *other* AI chats (a Socratic tutor prompt for Ciências da Natureza review sessions, and a gabarito-extraction prompt for turning a PDF into the CSV format `carregar_gabarito_csv()` expects). `manual_prioridade_de_estudo.md` (added 2026-08-28) is categorically different — it's read in-app, not pasted elsewhere: the mentality/strategy reasoning (TRI coherence, why a recurring-topic-you-can't-eliminate-by-interpretation like eletrodinâmica deserves base study before more simulados) behind why `prioridade_de_estudo()`'s ranking is the intended daily workflow. All three are surfaced read-only in the app's "Guia do Estudante" page (`render_guia_estudante()`, three-way `st.radio`, manual is the default/first tab). Editing any of them changes what's displayed/pasted, not any running code path — but the manual cites live numbers as a dated snapshot ("Retrato de hoje"), so if it's ever revised, update that snapshot and its date rather than leaving it stale indefinitely.
