# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal ENEM study system (Portuguese-language codebase/comments) for one user (Gabriel) preparing to retake the exam. `core/` is a from-scratch rewrite of a legacy prototype that lives one directory up (`enem_gi/main.py`, `enem_gi/app.py`) — the legacy system stored everything in a single CSV and had real bugs (schema collisions between scripts writing the same file, string-fragmented taxonomy like "Matemática Básica" vs "matemática básica", one video = one question with no room for a second resolution). `core/` replaces the CSV with a SQLite database (`enem.db`) plus a relational schema specifically to make those bug classes impossible by construction. The project root has a local git repository (initialized 2026-08, nothing pushed anywhere) — commit before risky changes, same as any other repo.

Do not "fix" the legacy files in the parent directory as part of work here — `core/` intentionally does not import from them except for one deliberate exception (see Cross-directory dependency below).

## Commands

There is no test suite, linter, or build step. This is a Streamlit app + a set of one-off/maintenance scripts.

- Run the app: `streamlit run cartao_resposta.py` (from inside `core/`)
- Load/update `enem.db` from source-of-truth CSVs: `python reconstruir_base.py` — backs up `enem.db` first (via `backup_db.py`) then updates in place; idempotent, safe to rerun (see the note under Architecture below)
- Smoke-test `db.py` in isolation: `python db.py` — this writes to `enem_teste.db`, never to `enem.db` (see the `__main__` block); safe to run anytime
- Extract an official gabarito from an INEP PDF: `python extrair_gabarito_pdf.py <arquivo.pdf> <ano> [caderno] [--ciencias]` — requires the `pdftotext` CLI (poppler-utils) on PATH; writes `gabaritos_reais/gabarito_<ano>_<caderno>_OFICIAL.csv` (Matemática, itens 136-180) or `..._CIENCIAS_OFICIAL.csv` (`--ciencias`, itens 91-135) — same PDF covers both areas, run it twice (with/without `--ciencias`) when both are missing for a caderno. `caderno` defaults to `azul` — always pass it explicitly for any other booklet color, e.g. `amarelo`/`cinza`/`rosa`, or this silently targets the azul filename; refuses to overwrite an existing file unless `--sobrescrever` is passed
- One-off backfill scripts (`classificar_2024.py`, and historically similar ones) are meant to be run once and read top-to-bottom before rerunning — they hardcode question numbers/answers for a specific gap in the data

Dependencies: `streamlit` and `pandas` (see `../requirements.txt`), and, transitively through `coletar_videos.py` → `main.py`, the Google API client libraries used for YouTube auth.

`reconstruir_base.py` no longer deletes `enem.db` — it backs it up (via `backup_db.py`) and updates in place, idempotently. `db.carregar_gabarito_csv(..., preservar_materia_classificada=True)` is what makes that safe: an already-`classificado` question keeps its current `materia` even under `sobrescrever=True`, so bulk-loading a gabarito CSV (whose `materia` column is often just a placeholder like `sem_video_pendente`) can't regress a classification gained later via video-title scraping or manual triage. UI callers (Admin paste, Triagem) don't pass that flag — there, `sobrescrever=True` is deliberate human correction and should win.

## Architecture

### Layering rule (important, stated explicitly in db.py's docstring)

`db.py` is a leaf module: it imports nothing from `main.py`/`app.py`/any UI module, and has no dependencies outside the standard library. Every other module in `core/` imports *from* `db.py`, never the reverse. If a UI module ever needs something that currently lives in the parent `main.py`, that logic must be promoted into `core/` (or a new shared module) — never imported back from `main.py` into `db.py`. The one sanctioned exception to "never depends on the parent directory" is `coletar_videos.py`, which does `sys.path.insert(...)` to import `main.py` from the parent for its already-working YouTube OAuth/playlist-fetch code (`autenticar_youtube`, `extrair_playlist_id`, `buscar_todos_os_videos`) rather than duplicating it.

### Data model (`schema.sql`, mirrored by `TAXONOMIA_VALIDA` in `db.py`)

- `questoes` — one row per real exam question. Primary key is `id_questao`, a canonical string `"{ano}_{caderno}_{numero}"` (e.g. `2024_azul_136`), generated by `gerar_id_canonico()`. Using this instead of e.g. a video link as identity means a question's identity doesn't depend on whether it has a resolution video yet.
- `resolucoes` — many-per-question (video and/or text resolutions), the main limitation the old CSV model couldn't express.
- `tentativas_usuario` — append-only log of every answer attempt. Never updated or deleted except by the gabarito-correction path described below.
- `estado_revisao` — one row per question ever attempted; the mutable "what to review today" pointer, deliberately kept separate from the immutable `tentativas_usuario` log.
- `historico_alteracoes` — audit trail: whenever `inserir_questao(sobrescrever=True)` changes an already-stored `materia` or `alternativa_correta`, the change (and how many past attempts got their `resultado` recalculated) is logged here.
- `topicos_validos` — DB-side mirror of `TAXONOMIA_VALIDA`; not enforced via FOREIGN KEY on purpose (see below).

### Closed taxonomy + classification pipeline

Subject (`materia`) values come from a closed set, `TAXONOMIA_VALIDA` in `db.py` (mirrored, for reference, in `schema.sql`'s `topicos_validos` table and in `prompt_extracao_gabarito.md`'s taxonomy block — keep these in sync manually if you add a subject). Text goes through this pipeline before being checked against the taxonomy:

1. `normalizar_texto()` — lowercase, strip accents (NFKD), collapse whitespace to `_`.
2. `canonicalizar_materia()` — first checks `SINONIMOS_MATERIA` (exact synonym map, e.g. `funcao_afim` → `funcao_1_grau`), then `_PADROES_MATERIA` (regex families for things like "função de/do 1º/1/primeiro grau" that a synonym dict can't enumerate practically).
3. Checked against `TAXONOMIA_VALIDA`.

There is intentionally **no FOREIGN KEY** from `questoes` to `topicos_validos`: a question whose subject doesn't match anything in the closed taxonomy still gets written to `questoes`, just with `status_classificacao='nao_classificado'`, instead of being rejected or dropped. This is what feeds the triage workflow — see below. When adding a new synonym/pattern, run "Reclassificar com as regras atuais" (triagem.py → `db.reclassificar_pendentes()`) to reprocess already-pending rows; adding the mapping in code alone does not retroactively reclassify existing data.

### Manual triage survives full rebuilds

`triagem.py` lets a human assign a subject to `nao_classificado` questions. Because `reconstruir_base.py` deletes and rebuilds `enem.db` purely from the official gabarito CSVs (which know nothing about manual corrections), every manual classification is *also* persisted to `gabaritos_reais/correcoes_manuais.csv`, and `reconstruir_base.py` explicitly replays that file after loading the official gabaritos. If you add another mutation path that changes a question's `materia` outside of `inserir_questao(sobrescrever=True)`, it needs the same "persist somewhere `reconstruir_base.py` will replay" treatment or it will silently be lost on the next rebuild.

### `sobrescrever` semantics and answer-key corrections

`inserir_questao(..., sobrescrever=True)` updates a row in place, keeping the same `id_questao` (so existing `resolucoes`/`tentativas_usuario` foreign keys stay valid). If the correct answer (`alternativa_correta`) actually changes, every existing attempt for that question has its `resultado` (`acertou`/`errou`) recalculated against the new answer, and the change is logged to `historico_alteracoes`. This is deliberate: a later, more trustworthy source (e.g. an official PDF gabarito) can correct an earlier guess without silently leaving stale acertou/errou values behind.

### Spaced repetition (simplified Leitner)

`_calcular_leitner()` in `db.py`: wrong answer → streak resets to 0, next review in 1 day. Correct answer → streak += 1, interval = `2^(streak-1)` days, capped at `TETO_INTERVALO_DIAS` (90). The interval is always recomputed from the current streak rather than incrementally adjusted, so it can never drift from a corrupted intermediate state — it's fully reconstructible from `tentativas_usuario` history. `registrar_tentativa()` is the *only* function that should write to both `tentativas_usuario` and `estado_revisao` (keeps them from diverging via separate writes).

### `gabaritos_reais/` naming convention

Source-of-truth CSVs consumed by `reconstruir_base.py`, matched by filename regex:
- `gabarito_<ANO>_<CADERNO>_OFICIAL.csv` → Matemática
- `gabarito_<ANO>_<CADERNO>_CIENCIAS_OFICIAL.csv` → Ciências da Natureza (same exam day/caderno, different `grande_area`)

Required CSV columns: `numero,materia,gabarito` (optional per-row `grande_area` override). Math and Ciências for the same year/caderno are stored as **separate** "provas" throughout the system (never merged into one 45+44-question grid), since they're graded and studied independently.

### Multiple cadernos (booklet colors) of the same year

A real INEP exam prints the same items in 4+ colors (azul/amarelo/rosa/cinza, and 2024 added verde) with different item ORDER per color — same content, different `numero`. Each `(ano, caderno, grande_area)` combo is stored as its own fully independent set of `questoes` rows (own `id_questao`, own `materia` classification, own attempts) — confirmed, deliberate design (Gabriel wants each color he practices to count as its own separate simulado attempt for média móvel/priority stats, not merged into one). Loading a new color for a year already partially loaded is just running `extrair_gabarito_pdf.py`/`reconstruir_base.py` again with that `caderno` — no special-casing needed, this is exactly the same code path as loading a brand-new year.

`db.simulados_completos_disponiveis()` (backs "Simulado completo" and the Calendário checklist) enumerates every `(ano, caderno)` pair that has BOTH areas loaded — a year can produce more than one entry (2024 has both azul-complete and amarelo-complete). An earlier version stored only one caderno per `(ano, area)` in a plain dict, so a second color for the same area silently overwrote the first the moment it was loaded — fixed by keying on sets of cadernos per area and emitting one combo per same-caderno match, falling back to a cross-caderno combo (2023's azul-math/cinza-ciências case) only when each area has exactly one candidate caderno. Any UI that lists these combos must label by caderno too (`f"{ano} — {caderno}"`), not just by `ano` — a bare-year key collides the same way the old data layer did.

### Cross-caderno video linking (`coletar_videos.py`)

The channel (Xequemat) pastes, in the video's YouTube **description** (not title), the same item's number in every color — confirmed against the real API response, and the opposite order from what the title's own "Questão N - Caderno X" format would suggest (color first, then number):
```
Caderno Azul - 136
Caderno Amarelo - 164
Caderno Rosa - 150
Caderno Cinza - 166
```
`extrair_cadernos_da_descricao()` parses this block; `processar_playlist()` uses it to link the SAME video (and propagate the SAME materia, if extracted from the title and the target question is still `nao_classificado`) to every color's corresponding `id_questao` — not just the color passed as the `caderno` argument. A color with no gabarito loaded yet just lands in the `cruzados_sem_questao` result bucket (harmless) — re-running the playlist collection later, after loading that color, picks up the missing links retroactively (no need to special-case "already tried this before"; `db.inserir_resolucao()`'s existing dedup makes it idempotent). Older videos without this description block fall back to the original single-caderno-only behavior unchanged.

### App structure (`cartao_resposta.py`)

Single Streamlit entry point with a sidebar-driven page switch (not a multi-file Streamlit app): Cartão-resposta (answer sheet + grading), Minha análise (dashboards: study-priority ranking blending recurrence x error rate, error-type breakdown, streak/rank gamification), Calendário (`db.plano_periodizacao()` phase + weakness ranking + `db.progresso_simulados()` checklist, all derived live from real data, never a fixed schedule), Objetivos (countdown, freeform "why", target scores vs. actual practice accuracy, photo vision board in `core/vision_board/`), Coletar vídeos (delegates to `coletar_videos.py`), Triagem (delegates to `triagem.py`), Admin (backup, daily goal, exam date, paste-CSV gabarito loader, `historico_alteracoes` viewer), Guia do Estudante (renders `guia_estudante.md` / `prompt_extracao_gabarito.md` verbatim). Theme (`.streamlit/config.toml` + `ui_theme.py`, injected once per run via `ui_theme.injetar_tema()`) applies globally regardless of which page function renders. `configuracoes` (key-value table in `schema.sql`) holds everything user-editable that isn't question/attempt data: `data_prova`, `data_inicio_plano` (set once, anchors `plano_periodizacao()`'s phase math -- never overwritten except when the exam date itself is edited in Admin), `meta_diaria`, `meta_nota_matematica`/`meta_nota_natureza`, `motivo_pessoal`.

Any `st.file_uploader` that saves on presence of a value (not gated behind its own `st.button`) is a bug waiting to happen: the uploader keeps its value across reruns until its `key` changes, so an unconditional `if arquivo: salvar(); st.rerun()` re-saves the same file every rerun forever (found and fixed once already in the vision-board uploader -- one test upload became ~500 copies in seconds). Every file-save path in this file either gates on an explicit button click, a widget `key` that increments after success, or both.

Cartão-resposta itself has 4 "Modo" options, all converging on `_renderizar_grade_questoes(questoes, sufixo)` -- the shared grid/grading/error-review core (extracted out of `_renderizar_bloco_prova()` in 2026-08 specifically so it could be reused by more than one exam-shaped source). "Uma prova por vez" and "Simulado completo" fetch via `db.listar_questoes_da_prova()` (one exam; `_renderizar_bloco_prova()` also shows the prova-specific attempt history). "Revisão de hoje" fetches via `db.questoes_para_revisar()` + `db.questoes_por_ids()` (whatever's overdue, any exam, order preserved). "Praticar por matéria" fetches via `db.questoes_por_materia()` (one subject, every year mixed together on purpose -- the one place in the app that deliberately breaks the "never mix exams" rule, because the point is cross-year practice of a weak subject). `_renderizar_bloco_prova()` is still called twice on one page (once per tab) for "Simulado completo" running Matemática and Ciências back to back -- every widget/session_state key is suffixed with `ano_caderno_area` (or the mode's own sufixo) to avoid collisions between calls.

Enunciado (`questoes.enunciado_texto` / `enunciado_imagem_path`, updated via `db.atualizar_enunciado()`) renders inline in the grid when present, with its own editor rendered OUTSIDE `_renderizar_grade_questoes()`'s `st.form(...)` -- a form allows exactly one submit button, so per-question "save enunciado" buttons can't live inside it. Uploaded images land in `core/enunciados/<id_questao>.<ext>`.

### `guia_estudante.md` / `prompt_extracao_gabarito.md`

These are not documentation about the code — they're copy-pasteable prompts for use in *other* AI chats (a Socratic tutor prompt for Ciências da Natureza review sessions, and a gabarito-extraction prompt for turning a PDF into the CSV format `carregar_gabarito_csv()` expects). They're surfaced read-only in the app's "Guia do Estudante" page. Editing them changes what the user pastes elsewhere, not any running code path.
